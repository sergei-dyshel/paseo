# Fork changes as plugins

Which of this fork's changes could be delivered as a Paseo plugin instead of a patch, and which plugin API is missing for the rest. The plugin API is [public-docs/plugins/reference.md](../public-docs/plugins/reference.md); the SDK plugins receive is [public-docs/sdk/reference.md](../public-docs/sdk/reference.md). See [fork.md](fork.md) for the branch shape.

This is a snapshot. It was evaluated on 2026-11-05 against upstream `v0.13.2`, the base of the 18 fork commits at the time, plus the uncommitted workspace title sync. Re-check the verdicts after a rebase: a new base may add the API a row says is missing.

## Result

None of the changes can be a plugin in full. Three can be partial, two have in-API workarounds with collateral, seven cannot be done at all, and six are build tooling or docs where plugins do not apply.

The common wall is the SDK handle plugins receive. `PaseoAgentHandle` (`packages/client/src/index.ts:347`) can read an agent but not rename it or change its mode, model, or effort, although the low-level daemon client has `updateAgent`, `setAgentMode`, `setAgentModel`, and `setAgentThinkingOption` (`packages/client/src/daemon-client.ts:3297`, `:3882`, `:3910`, `:3965`). Only `PaseoWorkspaceHandle.setTitle` mutates a title. Nothing lets a plugin reach inside the built-in Claude adapter, the Electron main process, or the app's notification path.

### Rubric

- **Full**: a documented plugin API delivers the README-visible behaviour.
- **Partial**: a documented plugin API delivers a user-visible subset on the same surface.
- **Workaround**: an in-API route reaches the outcome but changes something the fork commit does not, such as persisted host config.
- **No**: nothing a plugin can do reaches the surface the change affects.

Surrogates in other places, such as a composer pill standing in for a tab title, do not count. Out-of-API routes do not move a verdict; they are listed at the end because they exist.

## Missing plugin API, ranked by changes unblocked

1. **Agent title setter on the SDK handle.** The daemon RPC, permission mapping, and plugin admission already exist; `createPaseoApi` in `packages/client/src/index.ts` never wires `updateAgent`. Unblocks the Claude-to-tab rename, the workspace-to-agent direction of the title sync, and half of each rename commit.
2. **Agent lifecycle events** for title changes, including the stored-record path closed agents take, and post-registration resume and import events carrying the provider session id. The event catalog is a fixed list of nine names (`packages/server/src/server/plugins/lifecycle/index.ts:19-29`) and `agent.created` fires only on creation.
3. **A way to extend the built-in Claude adapter.** Five changes live inside it. A plugin provider cannot register the `claude` id (`packages/server/src/server/agent/provider-registry.ts:927`), and the provider protocol has no rename or activity events. The per-item alternatives are smaller: exempt hook env from the parent-session clearing, a catalog hook, a provider-level title control, a config-editable resume hook, translation of the background-tasks signal.
4. **Mode, model, and thinking setters** on the agent handle. The daemon already has `applyAgentConfig`. The only reachable path today is the undocumented `sessionMode` option on `send` (`packages/protocol/src/messages.ts:1397`, applied at `packages/server/src/server/agent/agent-prompt.ts:354`), which forces a prompt.
5. **Notification seams:** a client notify API with click routing and a composition hook, or a daemon-side attention-notification before-hook, which on upstream also covers the desktop text since the app shows the daemon body verbatim. Plus Electron bridge fields and a dismiss IPC, and a presence signal: the first `notifications: true` subscription per socket consumes `shouldNotify`, so a plugin's copy is always `false`.
6. **Sidebar and tab seams:** workspace menu item, row gesture handler, tab-strip action, and dispatch of built-in actions such as the existing rename dialogs.
7. **Focused tab per workspace** including terminal tabs. The layout store is off limits to plugins and the host derives a focused agent only for the active workspace.
8. **Terminal SDK parity:** the SDK schema strips the daemon's terminal `title`, and there is no terminal rename.
9. **`paseo` on `PluginServerContext`** (`packages/plugin/src/server/contracts.ts:30-43`). Only hook and handler contexts carry it, so a server-only plugin cannot start a subscription or patch config until its first hook or RPC fires.
10. **Workspace seams:** a status contribution API, a title-generation switch separate from commit and PR generation, and the creation hook on the `create_agent`, MCP, and schedule paths.
11. Smaller: `disabled` and `visible` on Command Center items; the client `useAgent` snapshot omits `runtimeInfo`, `pendingPermissions`, and `persistence` that the wire snapshot carries, so client code falls back to the SDK list subscription for them.

## Workarounds, exclusions, and doc gaps

The two workaround verdicts rely on `paseo.config.patch` (`packages/client/src/index.ts:473`) accepting `providers.claude.command` and `env`, which the store keeps (`packages/server/src/server/daemon-config-store.ts:307`) and the registry rebuilds without a restart. Both persist host config and take over Claude binary resolution, so they are not equivalent to the commits. One unverified route could matter for the entrypoint change: Claude Code's `--settings` file supports an `env` block and a plugin can pass a settings file per agent through `extraArgs`, but whether the CLI applies it before reading the entrypoint variable was not confirmed.

Excluded as out-of-API, although feasible on an unsandboxed daemon host: a second daemon client built from the published `@getpaseo/client` internal entry and the local credential file; spawning the `paseo` CLI from the plugin subprocess; DOM and `window.paseoDesktop` access through the shared JS realm; process-table scans for `PASEO_AGENT_ID`; scraping `daemon.log`.

Doc-versus-code findings worth upstreaming:

- The plugin reference advertises `agent.session_open` env injection without naming the four keys the sanitizer strips: `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SSE_PORT`, `CLAUDE_AGENT_SDK_VERSION`.
- The `sessionMode` option on `send` is an undocumented mode mutation.
- Runtime translations are marked unreleased but exist in 0.13.2.
- The Command Center is reachable on compact native via the sidebar Search row; the reference mentions only the keyboard shortcut.

## Method and limits

Each change was analysed against the plugin reference, the SDK reference, and the v0.13.2 code by one agent, then checked by two adversarial verifiers with different lenses, then a cross-cutting critic; the load-bearing claims were re-read in code afterwards. The fork touches none of `packages/plugin`, `packages/server/src/server/plugins`, `packages/app/src/plugins`, or `packages/client`, so the plugin code read equals upstream's. Everything is static analysis: no plugin was built or run. The Claude CLI's resume picker filter on the transcript's `entrypoint` field was confirmed from the installed binary.
